## 1. Correction: what a ddp-sync restart loses (Ramon remembered redis was added for this; he was right)
I had told Ramon a restart "orphans the run" (and your notes said "restarting ddp-sync drops a pipeline that is waiting"). **Not the whole run.** [read] `app.py` start-up calls `reconcile_inflight_fargate_jobs()` (OPEN-251): every launched Fargate scrape task is recorded in redis (`inflight_fargate_jobs`: run_id, jurisdiction, task_arn, load_task_arn) and after a restart ddp-sync **waits for that task again (fresh wait budget) and then loads it into RDS**. **Not resumed** [read]: the pipeline's later steps live in the original apscheduler coroutine (`openstates_scrape.py` calls `archive_with_retry` after the scrape), and the resume path never calls the archive, so for a restarted run the **archive and the LegBot/search/embedding hand-off do not run**; the **archive retry loop** (`ARCHIVE_RETRY_DELAYS_S = (1800, 7200)`, sleeping inside the coroutine) is dropped with its final alert; an **archive Fargate task in flight has no redis record** (it finishes on its own but ddp-sync loses its outcome and the hand-off); `clear_state_locks()` runs at start (all `ddp:pipeline_lock:*` cleared). Recovery: the archiver has no cutoff, so the next archive of the state (next run, or `POST /trigger/openstates-archive/<st>`) catches up. **No resume has been seen on this host yet** [seen: none in the saved logs], so it is untested here. **So the gate "ddp-sync must be idle" is about not dropping archives and their hand-offs, not about losing scrapes or loads.**
