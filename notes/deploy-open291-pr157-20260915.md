# Deploy instructions: ddp-sync PR #157 (OPEN-291, scrape-triggers-archive)

Merged to `ddp-sync` main. Not deployed anywhere yet.

## What it does

Adds a hook inside `_run_scrape()` that fires a jurisdiction's archive job right after
its own scrape completes -- automatically covers FL, WA, USA, and the whole secondary
batch (va/mi/ma/ut/az/nc), config-driven opt-in (a jurisdiction just needs to be in
`openstates_archive.jurisdictions`, no per-jurisdiction code). Alabama is untouched --
archived on its own schedule, never scraped by `ddp-sync` at all, so it never reaches
this hook. The existing weekly archive cron stays registered for every jurisdiction as
a floor/backstop; a new debounce (inside `_run_archive_with_hook`) keeps that backstop
from producing a duplicate run if it lands close to a hook-triggered one.

**This is the fix for the still-open MI archiving-lag problem** flagged in
`mi-retry-note-mislabeled-not-an-extraction-fix-20260915.md` -- newly-introduced MI
bills currently wait up to a week for MI's Thursday archive cron to reach them, which
is exactly what was masked by a manual sweep in that note's retest. Once this deploys
and a scrape actually runs for MI, this closes that gap going forward (though it won't
retroactively fix documents already stuck waiting -- that's still a one-off sweep if
needed in the meantime).

## Deploy steps (same as OPEN-140's PRs, ddp-sync's own README "Deployment" section)

**EC2 civic (systemd):**
```bash
cd /home/ubuntu/ddp-sync
git pull origin main
source .venv/bin/activate
pip install .
sudo systemctl restart ddp-sync
```

**Mac Studio (system LaunchDaemon) -- needs an admin account:**
```bash
cd /Users/agentsmith/Developer/repos/ddp-sync && git pull origin main
sudo launchctl kickstart -k system/com.ddp.ddp-sync
curl -s http://localhost:8001/ddp-sync/v1/schedule    # verify the six OpenStates jobs
```

Both hosts need this pulled -- no leader election, each runs its own independent
scheduler.

## What to check after deploying

Watch the logs for `scrape_triggered_archive_result` after the next scrape for any
covered jurisdiction (MI's own next scrape, or the secondary batch's next weekly run
otherwise) -- confirms the hook actually fired and what it found. If a jurisdiction's
archive job is skipped, `archive_debounced_skipping_duplicate_run` in the logs says why
(should only happen when a second attempt lands within ~30 minutes of an already-
successful one for the same jurisdiction).
